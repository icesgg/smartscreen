# 프로그램 자동 업데이트

새 버전을 서버에 올리면 모든 PC 가 스스로 알아채서 받아 가는 구조와, 그렇게
정한 이유. 자리비움 감지와는 상관이 없고, 같은 앱에 있는 이유는 Supabase
배관과 로그인이 이미 여기 있었기 때문이다 (클립보드 공유와 같은 사정).

관련 파일: `client/update.h` / `.cpp`, `client/version.h`, `client/relver.h`,
`tools/publish.cpp` + `publish.bat`, `supabase/releases.sql`,
`docs/dashboard.html` 의 "프로그램 업데이트" 칸.

---

## 왜 있나

프로그램을 고치는 일은 잦고, 고칠 때마다 PC 마다 zip 을 풀어 덮어쓰는 것은
손으로 하는 배포다. 손으로 하는 배포는 **어느 PC 가 어느 버전인지 아무도
모르게 되는 것**으로 끝난다. 그 상태에서 "안 된다" 는 보고가 오면 코드를
보기 전에 버전부터 물어야 하고, 대개 답을 못 듣는다.

---

## 두 가지 길

어느 길인지는 그 PC 가 기업 등록(`enterpriseRegistered` + `orgId`)이 돼
있는지로 갈린다.

| | 개인 PC | 기업 PC |
|---|---|---|
| 새 버전을 알아채면 | 간단 창 아래에 띠가 뜬다 | 승인된 것이면 바로 받는다 |
| 사람이 하는 일 | [업데이트] 를 누른다 | 없다. 관리자가 대시보드에서 승인한다 |
| 승인 안 된 새 버전 | 해당 없음 | "관리자 승인을 기다려요" 로 보이기만 한다 |
| 다시 시작 | 받은 직후 | 받은 직후 (아래 "가리는 중에는" 예외) |

기업 PC 에서 사용자에게 묻지 않는 이유는, 묻는 순간 조직 안의 버전이 다시
갈라지기 때문이다. 배포 시점을 정하는 사람은 프로그램을 만든 사람도
쓰는 사람도 아니라 그 조직의 관리자다 - 그래서 승인 표가 따로 있다.

## 서버에 무엇이 있나

| 표 / 버킷 | 담는 것 | 읽기 | 쓰기 |
|---|---|---|---|
| `releases` | 버전, 파일 경로, **SHA-256**, 크기, 메모, 켜짐 | 누구나 (켜진 것) | `release_admins` |
| `release_admins` | 올릴 수 있는 계정 | 자기 줄 | SQL Editor 만 |
| `org_release_approvals` | (조직, 버전) 승인 | 누구나 | 그 조직의 admin |
| Storage `releases` | exe 파일 | 누구나 | `release_admins` |

### 읽기는 열어 두고 쓰기를 지킨다

`device_tokens` / `clip_items` 와 정반대다. 저 둘은 anon 정책이 하나도
없는데, 여기는 로그인 없이 읽힌다 - **개인 PC 는 로그인이 없고 그 PC 도
업데이트를 받아야 한다.** 읽히는 것은 버전 번호와 파일이고, exe 는 어차피
나눠 주는 물건이다.

지켜야 하는 것은 쓰기다. `releases` 에 행을 넣을 수 있으면 모든 PC 에 실행
파일을 밀어 넣을 수 있다. 그래서 쓰기는 `release_admins` 만 하고, 그 표는
SQL Editor 에서만 고친다 (관리자가 관리자를 추가하는 길이 있으면 계정 하나가
새면 전부 샌다).

### 믿는 것은 해시 하나다

클라이언트는 받은 파일의 SHA-256 이 **행에 적힌 값**과 다르면 버린다. 그래서
버킷의 파일만 바꿔 놓아도 소용이 없다 - 행은 못 고치니까. 해시를 파일 옆에
`.sha256` 로 두는 방식을 쓰지 않은 이유가 이것이다. 파일을 바꿀 수 있는
사람은 그 옆의 파일도 바꿀 수 있다.

`Publish.exe` 는 올린 뒤 **anon 키만으로 다시 내려받아** 해시를 대조한다.
PC 들이 받는 길 그대로다. 이게 통과하면 버킷 정책과 파일이 둘 다 맞는
것이고, 실패하면 PC 들이 실패하기 전에 올리는 사람이 먼저 안다.

## 실행 중인 exe 는 자기를 덮어쓸 수 없다

그래서 자기 exe 를 `%APPDATA%\SmartScreen\update\updater.exe` 로 복사해 두고,
그 복사본을 `--apply-update <pid> <새 파일> <내 경로>` 로 띄운 뒤 정상
종료한다. 복사본은

1. 원래 프로세스(pid)가 끝나기를 기다리고 (최대 60초)
2. `SmartScreen.exe` 를 `SmartScreen.exe.bak` 으로 옮기고
3. 새 파일을 그 자리에 복사한 뒤 해시를 한 번 더 재고
4. 다르면 `.bak` 을 되돌리고, 맞으면 새 exe 를 띄운다

별도의 updater 프로그램을 만들지 않은 이유: 그것도 배포해야 하는 파일이다.
배포를 없애려는 기능이 배포할 것을 늘리면 안 된다. `--apply-update` 는
`--clip-test` 와 같은 자리에서, 뮤텍스보다 먼저 처리된다 - 원래 프로세스가
아직 살아 있을 때 시작되기 때문이다.

`.bak` 은 새 exe 가 무사히 떠서 `UpdateCleanupAfterStart()` 까지 왔을 때
지운다. 새 exe 가 시작조차 못 하면 `.bak` 이 남아 있어 손으로 되돌릴 수 있다.

복사본은 세 가지를 요구한다: 새 파일은 `%APPDATA%\SmartScreen\update\` 안에
있어야 하고, 바꿀 파일의 이름은 `SmartScreen.exe` 여야 하고, 새 파일의 해시가
넘겨받은 `--sha` 와 같아야 한다. 이게 없으면 `--apply-update` 는 아무 파일이나
바꾸는 도구가 된다. 해시는 내려받을 때 한 번, 여기서 한 번 더 잰다 - 받은
파일이 `%APPDATA%` 에 놓여 있는 사이에 바뀌었으면 두 번째에서 걸린다.

## 실패는 기억해야 한다

적용에 실패하면 복사본은 예전 exe 를 다시 띄운다. 그 exe 가 아무것도 모르면
같은 버전을 다시 받아 다시 적용하러 종료하고, 그게 끝없이 반복된다 - 기업 PC
는 묻지 않고 적용하므로 특히 그렇다. 그래서 복사본은 실패한 버전과 이유를
`%APPDATA%\SmartScreen\update\failed-<버전>.txt` 에 적고, 다음 확인은 그 버전을
"지난번에 적용하지 못했어요: …" 로만 보여 준다. 사용자가 [다시 시도] 를
누르거나(그때 기록을 지운다) 더 새 버전이 나올 때까지 저절로 다시 하지 않는다.

같은 이유로 **관리자 권한을 요구하는 폴더(Program Files)에서는 자동 적용을
하지 않는다.** UAC 창을 띄우고 답을 기다리는 동안 앱은 꺼져 있고 화면은
아무도 지키지 않는다. 그 경우는 "이 폴더에는 쓸 권한이 없어요 - 사용자 폴더로
옮기면 자동 업데이트가 돼요" 로 끝낸다. 실패를 알리는 대화상자도 같은 이유로
띄우지 않는다 - 예전 exe 를 먼저 띄우고, 그 앱의 띠가 기록을 읽어 이유를
보여 준다. 대화상자는 예전 exe 마저 못 띄웠을 때만 뜬다.

원래 프로세스가 120초 안에 끝나지 않으면 (종료 절차가 멎은 것이다) 끝내고
진행한다. 살아 있는 채로 파일을 바꾸면 새 exe 가 단일 실행 뮤텍스에 걸려
죽고, 원래 프로세스까지 끝나면 아무것도 남지 않는다. 반대편에서도 받아 준다:
새 exe 는 뮤텍스가 이미 있으면 바로 "이미 실행 중" 이라고 끝내지 않고 10초를
기다린다.

## 화면을 가리는 중에는 다시 시작하지 않는다

다시 시작하는 1~2초 동안 검은 화면이 사라진다. 자리를 비운 사람의 화면을
지키는 것이 이 프로그램의 일인데, 업데이트가 그 틈을 내면 안 된다. 그래서
준비가 끝나도 `g_bBlackActive` 이면 풀릴 때까지 기다린다 (재보기 마법사가
도는 중, 로그인 창이 열린 중도 같다). `main.cpp` 의 `UpdateTick` 이 1분마다
다시 본다.

## 얼마나 자주 물어보나

켤 때 한 번, 그 뒤 한 시간마다. 간단 창 머리의 `버전 x.y.z · 업데이트 확인`
단추를 누르면 바로 묻는다. 요청 하나는 작은 GET 이라 더 자주 물어도 되지만,
새 버전이 한 시간 늦게 도착하는 것은 아무에게도 문제가 아니다.

## 버전

`client/version.h` 의 세 숫자가 전부다. 새 버전을 내놓을 때 그것만 올린다.
`Publish.exe` 도 같은 헤더로 빌드되므로 서버에 적히는 버전과 exe 가 자기라고
믿는 버전이 같은 빌드에서 나온다 - `make_dist.bat` 가 exe 들을 손으로 복사하지
않는 것과 같은 이유다.

비교는 세 숫자를 숫자로 한다 (`client/relver.h`). `"1.10.0"` 은 `"1.9.0"`
보다 새 버전이다. 문자열로 비교했다면 반대가 됐을 것이고, 그 버그는 열
번째 마이너 버전에서야 나타난다.

같은 버전 번호로 다른 파일을 올리는 것은 `Publish.exe` 가 막는다 (`--force`
로만 뚫린다). 안 막으면 이미 받은 PC 와 아직 안 받은 PC 가 **같은 버전
번호로 다른 바이너리**를 돌리게 되고, 그건 버전을 관리하는 이유를 없앤다.

## 배포하는 사람이 하는 일

`release.bat` 을 더블클릭한다. 그것이 순서대로 한다:

```
version.h 패치 번호 +1  ->  배포 메모 묻기  ->  앱 정상 종료(오버레이 [종료] 와 같은 길)
->  do_build.bat  ->  Publish.exe (브라우저 로그인 -> 업로드 -> anon 대조 -> 행)
->  make_dist + SmartScreen-desktop.zip  ->  git commit "Release x.y.z" + push  ->  앱 다시 띄우기
```

그 다음 (기업) 대시보드 > 프로그램 업데이트 > 그 버전에 [승인].

`release.bat 1.2.0` 은 그 번호로, `-NoGit` 은 커밋·푸시를 빼고, `-DryRun` 은 빌드까지만
돌려 보고 번호를 되돌린다. 빌드가 실패하면 번호를 되돌리고(안 그러면 다음 시도가 두 번
올린다), 게시가 실패하면 번호는 둔다(같은 번호로 `release.bat x.y.z` 를 다시). 로직은
`tools/release.ps1` 에 있다 - .bat 은 한글을 못 담아서 실행기만 한다.

손으로 할 때의 순서도 같다: `version.h` 올리기 -> 앱 끄기 -> `do_build.bat` ->
`publish.bat --notes "..."`. 앱을 안 끄면 링크가 실패하고, 그러면 `Publish.exe` 가
낡은 빌드라고 거절한다.

`publish.bat --list` 가 서버의 목록을, `publish.bat --deactivate 1.2.3` 이 잘못
올린 것을 끈다. 끄는 것뿐이다 - 이미 받은 PC 는 그대로다. 되돌리려면 더 높은
번호로 예전 코드를 올린다.

내 PC 에서만 먼저 돌려 보려면 `--channel beta` 로 올리고 그 PC 의 config.ini 에
`updateChannel=beta` 를 둔다. stable 채널 PC 들은 그 행을 보지 않는다.

## 첫 번째 배포는 손으로 한다

지금 돌고 있는 PC 들에는 이 기능이 없다. 업데이트 기능이 든 첫 버전(1.1.0)은
예전처럼 zip 으로 한 번 깔아야 하고, 그 다음부터가 자동이다.

## 검토에서 나온 것 (2026-09-30)

첫 판을 독립 검토자 다섯(스레드·적용·UI·보안·네트워크)이 읽고, 나온 것 하나하나를
다시 셋이 반박하게 했다. 16건이 살아남았고 반박된 것은 없었다. 두 PC 에 깔기
전에 고친 것:

- **기업 PC 무한 재시작.** 적용이 실패하면 예전 exe 가 다시 떠서 같은 승인
  버전을 다시 받아 다시 종료했다. 실패를 기억하는 곳이 없었다 → 위 "실패는
  기억해야 한다"
- **긴 배포 메모로 즉사.** `swprintf_s` 는 넘치면 잘라 쓰지 않고 프로세스를
  끝낸다. 메모 370자면 그 채널의 모든 PC 가 1초마다 죽었다 → `_TRUNCATE` 와
  120자 자름
- **updater 를 못 띄우면 Ready 에 갇힘.** "곧 다시 시작해요" 만 보이고 오류가
  어디에도 없었다 → Failed 로 바꾸고, [다시 시도] 는 이미 검증된 파일이 있으면
  다시 받지 않고 바로 Ready 로 간다
- 되돌리기 결과를 안 봤다 → 되돌리기도 재시도하고, 그마저 실패하면 `.bak` 이름을
  바꾸라고 대화상자로 말한다 (실행할 파일이 없는 유일한 경우)
- 60초 뒤 살아 있는 프로세스 위에 덮어썼다 → 120초 + 강제 종료, 새 exe 는
  뮤텍스를 10초 기다림
- 오프라인일 때 한 시간마다 도는 확인이 "실패" 띠를 띄웠고 [나중에] 로 닫히지
  않았다 → 손으로 누른 확인만 띠에 띄우고, [나중에] 는 언제나 듣는다
- 적용 단계가 내려받을 때의 해시를 다시 안 봤다 → `--sha` 로 넘겨 다시 잰다;
  `--apply-update` 가 아무 파일이나 바꾸지 못하게 경로·이름을 제한
- `Publish.exe`: 같은 버전 확인이 실패하면 검사를 건너뛰고 덮어썼다 → 실패는
  중단; `--deactivate` 가 0 행에 닿아도 [OK] 를 찍었다 → 바뀐 행을 돌려받아
  확인; 한글 메모가 CP949 로 갔다 → `wmain` + UTF-8
- 확인 실패(`Pending` 에서 오프라인) 뒤 [다시 시도] 가 "받을 버전이 정해지지
  않았어요" 만 반복했다 → 후보가 있는지로 가른다
- 설정이 끝난 개인 PC 에서 띠는 숨겨진 창에만 떴다 → 새 버전마다 한 번, 초점을
  빼앗지 않고 간단 창을 띄운다

고친 것을 다시 검토(수정 13건 확인 + 새 눈으로 4차원 + 반박 3표)했다. 13건 전부 고쳐진
것으로 확정됐고, 회귀·신규가 14건(7가지) 나와 그것도 고쳤다:

- **복사본이 검증 실패 때 원래 프로세스가 끝나기 전에 예전 exe 를 띄웠다.** 새 인스턴스가
  뮤텍스에 걸려 "이미 실행 중" 으로 죽고, 원래 것까지 끝나면 아무것도 안 남는다 → pid
  대기를 맨 앞으로
- **exe 이름이 `SmartScreen (1).exe` 처럼 다르면** 앱은 종료되고 복사본은 거절하고 아무
  말도 없었다 → 앱을 끄기 전에 이름을 보고 띠로 말한다; 복사본도 거절할 때 예전 exe 를
  다시 띄운다 (dst 는 손대지 않았으니 안전하다)
- [나중에] 뒤의 손 확인이 실패하면 `dismissed` 가 남아 아무것도 안 보였다 → 손 확인은
  감춤을 풀고 언제나 Checking 을 거친다
