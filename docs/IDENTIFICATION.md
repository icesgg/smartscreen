# 페어링 없이 아이폰을 식별하는 방법

주소가 계속 바뀌는 아이폰을 블루투스 페어링 없이 "내 폰"으로 알아보는
구조를 간략히 정리한 문서. 설계 배경과 실측 근거는
[PROXIMITY.md](PROXIMITY.md)의 "Identifying the phone" 절에 있다.

---

## 문제

잠긴 아이폰의 광고에는 이름도 서비스 UUID도 없다. **15분쯤마다 바뀌는
랜덤 주소(RPA)만** 남는다. 저장해둘 만한 고정값이 하나도 없다.

예전 방식은 Windows 레지스트리의 IRK로 그 주소를 역산했는데, IRK는 LE
본딩이 있어야 생긴다 = PC마다 Phone Link 설정이 필요했다. 데스크톱
배포에서 설치의 최대 장벽이었다.

---

## 해법: 주소 대신 물어본다

```
[등록 — 1회, 계정]
  폰: 구글 로그인 → claim_device_token → 서버가 이 계정의 토큰을 확정
  PC: 구글 로그인 → 같은 행을 읽어 config 에 저장
      (블루투스가 개입하지 않는다. 폰이 옆에 없어도 된다)

[등록 — 1회, 블루투스]  ← 인터넷이 없을 때
  폰: 앱을 화면에 띄움 → iOS가 이름+UUID를 광고에 그대로 실음
  PC: 그 광고 중 가장 센 것에 연결 → 토큰 읽기 → config 에 저장
      (후보가 모호하지 않아 남의 폰을 집을 수 없다)

[평소]
  PC: 광고 스캔 → 묶인 주소면 그대로 RSSI 사용
      주소가 30초 침묵하면 (= 회전) → 후보 추려서 연결 → 토큰 대조 → 재결합
```

**토큰** — 앱이 설치 때 만든 16바이트 난수. `UserDefaults` 에 보관하고
읽기 전용 GATT 특성(`7A1C0021`)으로 노출한다. 폰에 딸린 값이라 PC가
바뀌어도 같다.

핵심은 특성에 `value:` 를 인라인으로 박아둔 것이다. CoreBluetooth 가 값을
캐시해 **앱을 깨우지 않고 직접 응답**한다. 그래서 잠금/백그라운드에서도
읽히고 배터리도 안 쓴다.

블루투스 등록은 **앱이 화면에 떠 있을 때만** 받는다. 잠긴 폰으로 등록하면
후보를 눈 감고 고르는 셈이라 옆자리 폰을 집을 수 있다.

---

## 계정으로 등록하기

블루투스 등록은 "가장 센 광고"를 고르는 일이라, 폰을 PC 옆에 두고 앱을
띄워 두는 절차가 따라붙는다. 계정을 쓰면 그 절차가 통째로 없어진다.
양쪽이 같은 구글 계정으로 로그인하고, 서버에 있는 같은 값을 받아간다.

`device_tokens` 는 계정당 한 행이고 RLS 로 자기 행만 보인다
(`supabase/device_tokens.sql`). 이 테이블은 `contents` 와 성격이 반대다 —
저건 공유하라고 있는 것이고 이건 비밀이다. **토큰을 아는 사람은 자기
기기로 같은 값을 흘려 남의 화면을 계속 열어둘 수 있다.** 그래서 anon
역할에는 정책을 하나도 주지 않았다. 공개 키만으로는 한 행도 안 읽힌다.

`claim_device_token()` 은 이미 행이 있으면 그 값을 돌려주고, 없으면 폰이
넘긴 값으로 만든다. 이게 **재설치를 복구한다**: 토큰은 `UserDefaults` 에만
있어서 앱을 지웠다 깔면 새 값이 생기고, 그러면 그 폰을 등록해 둔 PC 가
한꺼번에 못 알아본다. 서버가 원본을 들고 있으면 재설치한 앱이 옛 값을 도로
받아 가고, 특성을 다시 올려 그 값으로 응답한다 (`adoptToken`).

데스크톱에서 구글 로그인을 하는 방법은 하나뿐이다 (RFC 8252): 시스템
브라우저를 열고 `127.0.0.1` 로 결과를 받는다. 구글이 임베디드 웹뷰를
거부하므로 앱 안에 로그인 화면을 그릴 수 없다. 암시적 흐름이 아니라 PKCE 를
쓰는 것도 선택이 아니다 — 암시적 흐름은 토큰을 URL 프래그먼트로 주는데,
프래그먼트는 HTTP 요청에 실려 가지 않아 루프백 리스너가 영영 못 본다.

로그인은 하되 아직 폰이 올라오지 않은 상태는 **오류가 아니다.** 순서상
흔한 첫 실행이라, PC 는 "실패"가 아니라 "폰에서 먼저 로그인하라"고 말한다.

### 붙이면서 틀렸던 것

세 번 헛짚었고 셋 다 우리 코드 밖이었다. 기록해 둔다.

- **Supabase 에 다른 OAuth 클라이언트의 client_id 가 들어 있었다.** 구글은
  authorize 는 받아주고 토큰 교환에서만 거절했다 — `Unable to exchange
  external code`. Google Cloud 쪽은 그 클라이언트에 "한 번도 사용되지
  않았다"는 경고를 달고 있었는데, 같은 사실을 반대편에서 말한 것이었다.
- **리다이렉트 허용 목록에 `ssbeacon://login-callback` 이 없었다.** Supabase 는
  허용되지 않은 `redirect_to` 를 오류로 만들지 않고 **Site URL 로 조용히
  바꾼다.** 그래서 폰의 웹 화면이 엉뚱한 페이지에 멈춰 있었고,
  `ASWebAuthenticationSession` 은 `ssbeacon://` 을 못 봐서 성공도 실패도
  알리지 못했다. 앱에는 아무 문구도 안 뜬다.
- **서버가 이미 값을 들고 있으면 폰이 고장나 있어도 PC 는 성공한다.**
  PC 가 넣어 둔 행과 폰이 만든 행을 구분할 수 없기 때문이다. 폰 쪽을
  확인하려면 행을 먼저 지워야 한다 (`AuthTest --unclaim`).

폰은 여기서 디버깅할 수 없는 유일한 기계다. 그래서 실패 문구에 HTTP
상태코드와 응답 본문을 싣는다 — "실패했습니다" 로는 위 세 가지가 구분되지
않는다.

## 아무에게나 연결하지 않으려면

낯선 폰에 연결을 시도하는 건 느리고 무례하다. 그래서 1차 필터를 쓴다.

iOS가 백그라운드로 가면 서비스 UUID를 **Apple overflow 영역**으로 옮긴다.
제조사 데이터 `01` + 128비트 필드 형태이고, **UUID 하나당 비트 하나**가
켜진다.

| 조건 | 주소 4048개 중 |
|---|---|
| Apple type `0x01` 메시지 | 954 |
| 그중 17바이트 (= overflow) | **13** |
| 그중 비트 1개 (= UUID 하나 광고) | 우리 폰뿐 |

나머지 941개는 24바이트 `01 09 20 22 …` 형태라 **길이만으로 걸러진다.**

여기에 RSSI 하한(임계값 −10dB)을 더한다. 그보다 먼 폰은 어차피 화면을
열어둘 수 없으니 건드릴 이유가 없다.

### 비트는 신원이 아니다

- 광고 UUID가 바뀌면 같이 움직인다 (실측 116 → 85 → 31)
- 폰 재부팅은 견딘다. 그런데도 며칠 사이 한 번 옮겨간 적이 있다 (원인 미상)
- **같은 비트를 켠 남의 폰을 실제로 만났다.** 붙어서 토큰을 읽어 걸러냈다

그래서 비트는 후보를 좁히는 데만 쓰고, 신원은 토큰으로만 확정한다. 비트가
낡으면 "비트 1개짜리 전체"로 넓혀 다시 배운다 — 자가 치유된다.

## 연결은 신원 확인에만

**RSSI는 계속 광고에서 온다.** WinRT는 연결 RSSI를 안 주고,
CoreBluetooth의 `readRSSI()` 는 central 전용이라 peripheral 인 폰이 못
쓴다. 토큰 읽고 바로 끊는다 — 붙잡고 있으면 폰이 광고를 멈출 수 있다.

실패는 두 종류로 갈라 다룬다.

| 결과 | 의미 | 재시도 금지 |
|---|---|---|
| 붙었는데 신원 서비스 없음 | 남의 기기, **확정** | 10분 |
| 못 붙음 | 일시적일 수 있음 | 15초 |

섞으면 아닌 게 확실한 기기를 계속 찌르면서 맞는 기기에 쓸 시도를
낭비한다. 실측에서 맞는 주소인데도 Unreachable 이 다섯 번 연달아 난 적이
있어, 못 붙은 쪽은 빨리 다시 해보는 편이 낫다.

연결 시도는 별도 스레드에서 한다. 한 번에 최악 10초라 스캔 콜백에서 하면
안 된다.

---

## UUID를 왜 둘로 나눴나

| UUID | 올리는 쪽 | 용도 |
|---|---|---|
| `7A1C0010` | **PC** | 폰이 central 로 붙는 연결 경로 (TICK / RSSI) |
| `7A1C0020` | **폰** | PC가 central 로 붙어 읽는 신원 |
| `7A1C0021` | 폰 | 토큰 특성 (read, 16바이트) |

같은 값을 쓰면 폰 앱의 central 스캔이 **옆자리 폰을 PC로 착각해** 붙으려
든다.

---

## 실측으로 확인된 전제

잠기고 **페어링 안 된** 아이폰이 Windows의 연결을 받아주고, 서비스 탐색에
응답하고, 토큰을 돌려준다. 본딩도 레지스트리도 개입하지 않는다.

이게 안 되면 설계 전체가 무너지므로, `tools/probescan.cpp` 로 먼저
확인하고 시작했다. 같은 도구가 배포 묶음에도 들어 있어, 현장에서 "폰이
문제인지 PC가 문제인지" 가르는 데 쓴다.
